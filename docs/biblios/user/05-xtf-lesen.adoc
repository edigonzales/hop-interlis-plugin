[[xtf-lesen]]
== XTF lesen: INTERLIS Input

`INTERLIS Input` liest XTF 2.3 oder 2.4 und liefert typisierte Zeilen einer konkreten Klasse. Andere Klassen werden übersprungen. Für einen gemeinsamen Strom aller Klassen verwenden Sie Transfer Input.

=== Datei, Modell und Klasse

[cols="2,2,3"]
|===
| Dialogfeld | Default | Verwendung
| Data file | leer | Lokaler Pfad zur XTF-Datei; Hop-Variablen sind möglich.
| Models | `%DATA` | Modelle aus dem Transferheader erkennen oder Modellnamen mit `;` trennen.
| Model dirs | Standardmodellquelle (siehe unten) | Lokale Verzeichnisse und Repository-URLs, getrennt durch `;`.
| Class | leer | Voll qualifizierter Name `Modell.Topic.Klasse`.
| Default SRID | leer | Optionale SRID-Kennung für erzeugte Geometrien.
| Source object field | `+_ili_source_object+` | Feldname für das optional mitgeführte Quellobjekt.
|===

Die Standardmodellquelle besteht aus `+%XTF_DIR+`, https://models.interlis.ch und https://models.geo.admin.ch, im Eingabefeld durch `;` getrennt.

`+%XTF_DIR+` bezeichnet das Verzeichnis der Transferdatei. `%DATA` ermittelt Modellnamen, nicht die Modelltexte: `.ili`-Dateien und ihre Imports müssen über die Modellverzeichnisse verfügbar sein. Für Offline-Läufe setzen Sie `Model dirs` auf lokale Verzeichnisse, wie in den Tutorials.

Eine noch nicht aufgelöste Variable oder fehlende Datei kann die Vorschau verhindern. Der Dialog bleibt geöffnet und zeigt eine Diagnose. Setzen Sie die benötigten Variablen und verwenden Sie `Reload model` zum erneuten Laden; damit wird auch der kompilierte Modellcache invalidiert.

=== Technische Felder und Vorschau

Unter `Reserved fields` sind `+_ili_tid+` und `+_ili_bid+` standardmässig aktiv. `+_ili_class+`, `+_ili_topic+` und `+_ili_operation+` sind standardmässig deaktiviert. Aktivieren Sie die Operation für inkrementelle Transfers. Löschobjekte benötigen eine Verarbeitung, die ihre Operation berücksichtigt; sie enthalten nicht die normalen fachlichen Attributwerte.

Die Schema-Vorschau zeigt den vorberechneten Mappingplan. Einwertige Strukturen werden abgeflacht, etwa zu `+Adresse_Strasse+`. Die konkrete Klasse enthält ihre geerbten Attribute. Der Dialog stellt keinen wählbaren Vererbungs- oder Flatten-Modus bereit.

Mehrwertige Attribute werden mit einem Hinweis auf Explode/Collect ausgelassen. Das gilt auch für primitive LIST/BAG. Skalare Referenzattribute liefern `+<Pfad>_ref+` und `+<Pfad>_ref_bid+`. Einfache Assoziationsrollen liefern ihre Rollenreferenzen; komplexe Assoziationen haben einen eigenen Zeilentyp.

=== Quellobjekt mitführen

Aktivieren Sie `Keep source object for Structure Explode`, wenn Sie Sammlungen mit Explode lesen oder unprojizierte Objektinhalte später per Overlay erhalten möchten. Das technische Feld enthält dann das vollständige INTERLIS-Objekt. Im Writer muss dasselbe Feld als `Source object field` eingetragen werden.

Ohne Quellobjekt erhalten Sie eine einfache Projektion. Ein Klasseninput mit Quellobjekt erhält weiterhin nur die ausgewählte Klasse; Header, vollständige Basket-Metadaten und andere Klassen benötigen den Ereignisweg.

=== Geometrien

Jedes unterstützte Geometrieattribut erzeugt ein eigenes Geometry-Feld. Kreisbögen bleiben über SQL/MM-WKB und den gemeinsamen Geometry-Typ erhalten. Gerade XYZ-Geometrien sind unterstützt; echte 3D-Kurven werden abgelehnt.

`Default SRID` setzt eine Kennung und führt keine Koordinatentransformation durch. Eine leere Einstellung ist keine Zusage einer bestimmten EPSG-Kennung. Kontrollieren Sie Modell und Daten vor dem Setzen.

=== Puffer und Ausgabezeitpunkt

`Options…` öffnet `Buffer memory (MiB)` (64), `Spill directory (empty: system temp)` (leer: Java-Tempverzeichnis) und `Maximum spill (MiB, 0: unlimited)` (0: ohne zusätzliche Obergrenze).

Normale Objekte werden fortlaufend gelesen. Bei bestimmten attributierten Assoziationen muss der vollständige Basket für die Linkauflösung vorliegen. Er wird bei Bedarf auf Disk ausgelagert. Erst nach Basket-Abschluss werden die betroffenen Zeilen einzeln projiziert und ausgegeben. Widersprüchliche Linkobjekte führen zu einem Fehler.

Das Pufferbudget ist keine JVM-Heap-Obergrenze: ein einzelnes IOM-Objekt und sein bearbeitetes Ergebnis müssen in den Heap passen. Details und dieselben Einstellungen für andere Transforms stehen unter <<puffer,Puffer und grosse Daten>>.

=== Daten validieren

Die modellbasierte Projektion ersetzt keine vollständige Transferprüfung. Verwenden Sie den separaten `INTERLIS Validate`-Transform für eine bestehende Datei. Beim Schreiben kann `Validate before publication` die temporäre Ausgabe prüfen. <<validierung,Die Validierungsanleitung>> beschreibt Optionen und Diagnosefelder.
