== Beispiele

Die neun Tutorials verwenden minimale lokale INTERLIS-2.4-Modelle und Transfers. Alle Fixtures liegen einmalig unter `docs/biblios/user/examples/`; die Testressourcen übernehmen diese Dateien. Die verlinkten Pipelines werden in der installierten Hop-E2E-Suite direkt ausgeführt.

=== Vorbereitung und Parameter

Installieren Sie Hop 2.19.0 mit Java 21 und die kompatiblen Plugin-ZIPs. Für GeoPackage ist zusätzlich Vector/Raster erforderlich. Verwenden Sie eine lokale Pipeline-Run-Konfiguration namens `local`, oder ersetzen Sie `-r local` durch deren Namen. Erstellen Sie ein Ausgabeverzeichnis. `+E2E_INPUT_DIR+` bezeichnet das absolute Fixture-Verzeichnis, `+E2E_OUTPUT_DIR+` das Ausgabeverzeichnis. In den neuen Pipelines sind beide als Parameter deklariert; die älteren E2E-Pipelines verwenden dieselben Namen als Hop-Variablen.

[source,bash]
----
mkdir -p /tmp/interlis-tutorial-output
"$HOP_HOME/hop-run.sh" -r local \
  -f examples/primitive-collections/primitive-collections.hpl \
  -p E2E_INPUT_DIR="$PWD/docs/biblios/user/examples" \
  -p E2E_OUTPUT_DIR=/tmp/interlis-tutorial-output
----

Starten Sie Folgeläufe erst nach dem erfolgreichen Ende des schreibenden Laufs. Die XTF-Writer veröffentlichen am Pipeline-Ende. Die Tutorials verwenden ausdrücklich `Overwrite existing file`; prüfen Sie den Ausgabepfad vor dem Lauf.

[cols="1,1,1,2"]
|===
| Eltern-TID | Eltern-BID | Index | Code
| g1 | b1 | 0 | Q100
| g1 | b1 | 1 | Q200
|===

`doc-liste-roundtrip.xtf` enthält beide Qualitäten in dieser Reihenfolge. `doc-liste.csv` enthält die Elternfelder `+_ili_tid+`, `+_ili_bid+`, `Name` mit `g1`, `b1`, `Rathaus`.

*Variante Filtern:* Nur Q100 behalten entfernt Q200 und lässt Index 0 gültig. Nur Q200 behalten erfordert bei strikter Reihenfolge einen neuen Index 0. Bei allgemeineren Filtern nummerieren Sie die verbliebenen Kinder je `(BID, Elternschlüssel)` ab 0 neu. Collect ersetzt die ganze Sammlung und prüft die Modellkardinalität.

==== Pipeline und Felder

https://github.com/edigonzales/hop-interlis-plugin/blob/main/examples/primitive-collections/primitive-collections.hpl[`examples/primitive-collections/primitive-collections.hpl`] führt vier Explode/Collect-Stufen nacheinander aus. Der Input behält `+_ili_source_object+` und kopiert den Elternstrom je Stufe in Eltern- und Kindzweig. Jede Stufe wählt eines der Attribute `Texte`, `Zahlen`, `Flags`, `Farben`. Collect verwendet ausdrücklich BID plus Elternschlüssel und `PRESERVE`; für primitive Werte ist kein Kindobjekt nötig.

[cols="1,1,2,3"]
|===
| Attribut | Typ von `+_ili_value+` | Werte in Indexfolge | Index
| Texte | String | erster, zweiter | 0, 1
| Zahlen | Integer | 7, 7, 9 | 0, 1, 2 (technisch für BAG)
| Flags | Boolean | true, false | 0, 1
| Farben | String | rot, blau | 0, 1
|===

Alle Kindzeilen von o1 haben `+_ili_parent_tid=o1+` und `+_ili_parent_bid=b1+`. Das Elternschema enthält nur `+_ili_tid+`, `+_ili_bid+`, `Name` und den optionalen Quellobjektträger; die Sammlungen erscheinen nicht als Skalarfelder.

==== Ergebnis und Varianten

`doc-sammlungen.xtf` enthält beide Elternobjekte. o1 behält alle Werte, die LIST-Reihenfolge und beide Vorkommen von 7. BAG hat keine fachliche Reihenfolge; dieser unveränderte Lauf liefert dieselbe Folge zurück. o2 erzeugt null Kindzeilen und hat nach Collect weiterhin vier leere Sammlungen.

Die Kardinalität jeder Sammlung ist 0..3. Ein viertes Element wird beim Sammeln abgelehnt. Bei Mindestkardinalität 1 wäre ein vollständig leer gefilterter Kindstrom ebenfalls unzulässig. Ändern Sie LIST-Indizes für eine neue Reihenfolge zu einer eindeutigen lückenlosen Folge ab 0 und sortieren Sie die Kindgruppe entsprechend.

==== Pipeline und Einstellungen

https://github.com/edigonzales/hop-interlis-plugin/blob/main/examples/child-preserve/child-preserve.hpl[`examples/child-preserve/child-preserve.hpl`] liest `DemoErhaltung.Daten.Eltern` mit Quellobjekt. Explode wählt `Kinder`; die gespeicherte Auswahl `selectedChildFields=Name` ist in der vorbereiteten Pipeline enthalten. Der aktuelle Explode-Dialog hat keinen eigenen Auswahl-Control für diese Projektion.

Die Kindzeile hat `+_ili_parent_tid+`, `+_ili_parent_bid+`, `+_ili_index+`, `Name`, `+_ili_child_object+`. `Versteckt`, `Zusatz` und `Details` stehen nicht als bearbeitbare Felder in diesem Kindstrom.

`Filter rows` behält `Name=bleibt` und leitet das andere Kind in einen Dummy-Zweig. Collect verwendet als unmittelbaren Kindinput `Behalten`, als Auswahl `Name`, als Modus `PRESERVE` sowie BID plus Elternschlüssel. Das verbleibende Kind hat bereits Index 0. Output verwendet den Elternträger und validiert die vollständige temporäre Datei vor Veröffentlichung.

==== Erwartete Erhaltung und Entfernung

`doc-erhaltung.xtf` enthält Elternobjekt e1 im Basket b1 und genau ein Kind:

* konkreter Typ `DemoErhaltung.Daten.SpezialKind`;
* Name `bleibt`;
* verborgenes Attribut `Versteckt=erhalten`;
* Untertypattribut `Zusatz=Untertyp`;
* verschachtelte Detail-LIST mit `innen eins`, `innen zwei` in dieser Reihenfolge.

Das zweite Kind `entfaellt` wird entfernt, obwohl es im ursprünglichen Elternträger vorhanden war. Für das erhaltene Kind kopiert Collect den Kind-Carrier und überschreibt nur Name. Eine Änderung dieses projizierten Feldes lässt die übrigen Inhalte bestehen. `REBUILD` könnte diese Erhaltung nicht aus der blossen Name-Spalte ableiten. Fehlende oder inkompatible Kind-Carrier führen mit `PRESERVE` zu einem Fehler.

. Erst nach erfolgreichem Pipeline-Ende https://github.com/edigonzales/hop-interlis-plugin/blob/main/examples/reference-roundtrip/reference-check.hpl[`examples/reference-roundtrip/reference-check.hpl`] ausführen. Diese Pipeline liest die neue XTF-Datei aus `+E2E_OUTPUT_DIR+` und erzeugt `doc-referenzen-check.csv`.

Die Parameter sind in allen drei Läufen gleich. Wiederholen Sie den oben gezeigten `hop-run.sh`-Aufruf mit dem jeweiligen Pipelinepfad in dieser Reihenfolge.

==== Ergebnis

Beide CSV-Prüfungen zeigen exakt:

[source,text]
----
_ili_tid;_ili_bid;Name;Intern_ref;Intern_ref_bid;Extern_ref;Extern_ref_bid
o1;b1;verweist;z1;;z2;b2
----

Die interne Referenz z1 benötigt keinen Referenz-BID; die externe z2 trägt b2. Null im projizierten TID-Feld entfernt eine Referenz beim inversen Mapping. Ein Referenz-BID ohne TID wird abgelehnt.

Der Ereignis-Roundtrip erhält zusätzlich die Zielobjekte: Basket b1 enthält z1 und o1, Basket b2 enthält z2. Reihenfolge, Namen und Referenzmetadaten werden im Paket-Test verglichen. Ein alleiniger Klassenroundtrip für Objekt würde die Zielklasse nicht mitliefern.

Der Writer validiert die temporäre vollständige Datei einschliesslich zweitem Durchlauf. Erst nach erfolgreichem Abschluss aller Pipeline-Zweige wird veröffentlicht. Bei Fehlern bleibt eine bestehende Ausgabe erhalten. Die separate Prüfpipeline demonstriert den Zeitpunkt, ab dem die neue Datei verfügbar ist.
