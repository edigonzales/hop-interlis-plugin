[[erweiterte-transforms]]
== Erweiterte Transforms

Diese Transforms ergänzen die typisierte Klassenverarbeitung. Die generischen Objektfelder sind technische Träger; für fachliche Bearbeitung projizieren Sie gezielt auf typisierte Zeilen.

[[modellmigration]]
=== Modellmigration mit ilimap

Öffnen Sie eine `.ilimap`-Datei direkt in Hop. Der native Editor zeigt links Regeln und Strukturkontexte, rechts Quell- und Zielschema sowie die Zuordnungen der gewählten Regel. `Load models` lädt die Modelle asynchron. Ziehen Sie eine Quellklasse auf eine Zielklasse oder ein Quellattribut auf ein Zielattribut. Eine bestehende Klassenregel behält beim Ändern ihres Ziels ihre technische ID; kontrollieren Sie anschliessend deren Attributzuordnungen.

`Edit expression` bearbeitet einen Ausdruck. `Insert function` bietet die Funktionen von ilitransformer samt Parametern an. Die Graphansicht zeigt den ausgewählten Ausdruck. `Enumeration table` ordnet jeden Quellwert einem Zielwert zu; nicht zugeordnete Werte führen bei der Ausführung zum Fehler. `Reference` verknüpft eine Quellreferenz mit der Regel, welche das Zielobjekt erzeugt.

Die DSL bleibt massgebend. Änderungen in beiden Ansichten sind mit `Undo` und `Redo` rückgängig zu machen. Syntax-Highlighting, Zeilennummern, Einrückung und Klammermarkierungen unterstützen die Texteingabe. Bei unvollständiger Syntax bleiben Text und Farben sichtbar, während grafische Änderungen pausieren. Kommentare und nicht grafisch unterstützte Definitionen bleiben erhalten. Beim Speichern erkennt der Editor zwischenzeitliche Änderungen durch andere Programme.

`Prepare migration` fragt Quellmodell, Zielmodell, Modellverzeichnisse und Dateipfade ab. Es erzeugt explizite Übernahmevorschläge und weist auf offene Unterschiede hin. Prüfen Sie neue Pflichtattribute, Umbenennungen und nicht zugeordnete Quellinhalte und bestätigen Sie die Entscheidungen mit `Confirm review`. Geänderte Modelldateien werden anhand ihrer Prüfsumme erkannt und verlangen eine erneute Prüfung; die Ausführung ergänzt keine stillen Zuordnungen.

`Check mapping` prüft die Definition ohne Datenausführung. `Preview complete XTF` verarbeitet und validiert eine vollständige kleine Beispieldatei in einem temporären Verzeichnis. Die Anzeige ist auf 100 Objekte begrenzt; die Verarbeitung liest die vollständige Datei einschliesslich der Referenzziele. Die Prüfung eines Beispiels ersetzt die Validierung des produktiven Bestands nicht.

Für den produktiven Lauf verwenden Sie die Workflow-Action `INTERLIS Migration`:

[cols="2,3"]
|===
| Einstellung | Bedeutung
| `Mapping (.ilimap)` | Gespeicherte Mappingdefinition.
| `Original XTF`, `Target XTF` | Optionale Überschreibungen der Dateipfade aus der Definition.
| `Additional model directories (;)` | Zusätzliche Modellverzeichnisse.
| `Report directory` | Optionales Verzeichnis für Berichte und Validierungsdiagnosen.
| `Validate complete output before publishing` | Standardmässig eingeschaltet.
| `Overwrite existing target` | Standardmässig ausgeschaltet.
|===

Hop-Variablen werden in diesen Action-Feldern aufgelöst. Relative Pfade innerhalb der DSL beziehen sich auf deren Datei; die DSL selbst expandiert keine Hop-Variablen. Original und Ziel müssen verschiedene Dateien sein. Die Action führt den gesamten Java-Migrationsjob aus, validiert die temporäre Ausgabe und veröffentlicht sie erst bei Erfolg. Fehler und Abbruch verhindern die Veröffentlichung.

Die erste Version unterstützt eine XTF-Quelle und ein XTF-Ziel. Eine Sammlungsebene lässt sich grafisch bearbeiten; tiefere explizite Strukturregeln bleiben über die DSL zugänglich. Joins, Aufteilungen und Hop-Unterpipelines haben noch keine grafischen Bedienelemente. Die Engine hält ihre Indizes und Zielobjekte im Speicher. Sie verwendet nicht die Spill-Budgets von `INTERLIS Output` und `Update`. Ein lauffähiges Beispiel steht im Repository unter `examples/migration/`.

=== INTERLIS Transfer Input

Der Dateiinput hat `Data file`, `Models`, `Model dirs` und `Mode`. Default ist `OBJECTS`. `EVENTS` liefert zusätzlich `+START_TRANSFER+`, `+START_BASKET+`, `+END_BASKET+` und `+END_TRANSFER+`. Objektzeilen verwenden `OBJECT`; Löschoperationen werden über `+_ili_operation=DELETE+` dargestellt.

Beide Modi verwenden dasselbe Schema:

[cols="2,1,3"]
|===
| Feld | Hop-Typ | Inhalt
| `+_ili_event_type+` | String | Ereignisname
| `+_ili_model+`, `+_ili_topic+` | String | Modell und qualifizierter Topicname
| `+_ili_bid+` | String | Basket-ID
| `+_ili_class+`, `+_ili_tid+` | String | Klasse und Objekt-ID
| `+_ili_operation+` | String | NONE/INSERT/UPDATE/DELETE
| `+_ili_object+` | InterlisObject | Objektträger; bei Grenzereignissen null
| `+_ili_line+`, `+_ili_column+` | Integer | Quellposition, soweit verfügbar
| `+_ili_basket_consistency+`, `+_ili_basket_kind+` | String | Basket-Metadaten
| `+_ili_basket_start_state+`, `+_ili_basket_end_state+` | String | Basket-Zustände
| `+_ili_transfer_metadata+` | String | JSON-Träger unterstützter Transfermetadaten
|===

Die Reihenfolge ist genau die Tabellenreihenfolge, innerhalb zusammengefasster Zeilen von links nach rechts. Bei Ereignissen bleiben nicht zutreffende Werte null. `OBJECTS` liefert keine vollständige Transferfolge und erhält insbesondere keine leeren Baskets allein über Objektzeilen.

=== INTERLIS Transfer Output

Konfigurieren Sie `Data file`, `Models`, `Model dirs`, `Overwrite existing file` und `Event mode`. Default ist Objektmodus (`Event mode` aus). `Options…` enthält dieselbe Validierung vor Veröffentlichung wie der typisierte Writer.

Im Objektmodus müssen die BIDs zusammenhängend gruppiert sein. Im Ereignismodus muss die Reihenfolge vollständig und gültig sein:

[source,text]
----
START_TRANSFER
  START_BASKET B1
    OBJECT ...
  END_BASKET B1
  START_BASKET B2
    OBJECT ...
  END_BASKET B2
END_TRANSFER
----

Ein abgeschlossener BID darf nicht erneut eröffnet werden. Verlorene Grenzereignisse, widersprüchliche BIDs oder ein fehlendes `+END_TRANSFER+` führen zu einem Fehler. Die Ausgabe wird erst am erfolgreichen Pipeline-Ende veröffentlicht; siehe <<xtf-schreiben,Ausgabesicherheit>>.

=== INTERLIS Object to Row

`Models`, `Model dirs` und `Class` wählen den Mappingplan. `Object field` ist standardmässig `+_ili_object+`. `+Include _ili_tid+` und `+Include _ili_bid+` sind aktiv; `Append typed fields to envelope fields` ist aus. `Default SRID` ist leer.

Ohne Append liefert der Transform das typisierte Klassenschema. Mit Append bleiben die eingehenden Envelope-Felder erhalten und fachliche Felder werden angefügt. Das Objektfeld steht damit als technischer Träger zur Verfügung. Es werden nur passende Objekte der konkreten Klasse projiziert. Für assoziationsabhängige Projektion kann die erste Ausgabe bis zum Basket-Abschluss warten; `Options…` enthält die Puffer-Einstellungen.

=== INTERLIS Row to Object

`Models`, `Model dirs`, `Class` und `Basket ID field` (`+_ili_bid+`) steuern das inverse Mapping. Die TID kommt aus `+_ili_tid+`. `Source object field (blank = automatic)` und `Operation field (blank = automatic)` können einen Träger beziehungsweise eine Operation ausdrücklich binden. Automatische Erkennung berücksichtigt die technischen Standardfelder.

Das Ergebnis ist das kanonische Envelope-Schema mit einer `OBJECT`-Zeile. Für Mehrklassenverarbeitung müssen alle Zweige dieses Schema liefern. Ein Quellobjekt ermöglicht Overlay; ohne Träger wird ein Objekt aus projizierten Feldern aufgebaut.

[[structure-explode]]
=== INTERLIS Structure Explode

Der Transform löst primitive oder strukturierte LIST/BAG-Attribute in Kindzeilen auf. Er benötigt ein vollständiges Elternobjekt im `Source object field`, standardmässig `+_ili_source_object+`. Aktivieren Sie dafür im Klasseninput `Keep source object for Structure Explode`.

[cols="2,2,3"]
|===
| Control | Default | Bedeutung
| Models / Model dirs / Class | Modellverzeichnisse wie Input; Modelle/Klasse leer | Elternklasse und Modellquelle
| Structure | leer | Pfad des Mehrfachattributs, auch einer primitiven Sammlung
| Source object field | `+_ili_source_object+` | Objektträger des Elternobjekts
| Parent TID field / Parent BID field | `+_ili_tid+` / `+_ili_bid+` | Identität aus der Elternzeile
| Parent key field | `+_ili_parent_tid+` | Name des Kind-Elternschlüssels
| Index field | `+_ili_index+` | Name der Position
| Copy parent fields | leer | Kommagetrennte Elternfelder zusätzlich mitführen
| Emit parent BID field | an | Kind-BID als `+_ili_parent_bid+` mitführen
| Emit technical index for BAG | an | Technische BAG-Position ausgeben
| Options… → Keep child source object | an | Strukturkind als `+_ili_child_object+` erhalten
|===

Kindfelder einer primitiven Sammlung sind `+_ili_parent_tid+`, bei aktiviertem BID zusätzlich `+_ili_parent_bid+`, `+_ili_index+` sowie `+_ili_value+` mit dem Typ des Elements. LIST erhält ihre Reihenfolge; BAG behält Duplikate, hat jedoch keine fachliche Reihenfolge. Eine leere Sammlung erzeugt keine Kindzeile.

Strukturkinder liefern die projizierten Strukturfelder und bei aktivierter Option `+_ili_child_object+`. Dieser Träger enthält den konkreten Untertyp, unprojizierte Attribute und verschachtelte Sammlungen. Fehlende Träger lassen sich später nicht durch `PRESERVE` rekonstruieren.

Die gespeicherte Konfiguration `selectedChildFields` wählt Attributpfade; leer bedeutet alle projizierbaren Felder. Der aktuelle Explode-Dialog hat dafür keinen eigenen Feldauswahl-Control. Das vorbereitete <<beispiel-h,Erhaltungsbeispiel>> enthält die Auswahl `Name` bereits in der `.hpl`-Datei. Der Dialog bewahrt diese Auswahl beim Speichern. Collect bietet die entsprechende Auswahl unter `Options…`.

Explode erzeugt die Kinder einzeln. Das Elternobjekt selbst muss weiterhin vollständig in den Heap passen.

[[structure-collect]]
=== INTERLIS Structure Collect

Collect erhält einen Elternstrom und einen Kindstrom. Es gibt pro Elternzeile eine aktualisierte Elternzeile mit Quellobjekt aus. **Der Kindstrom ersetzt die gesamte ausgewählte Sammlung.** Herausgefilterte Kinder werden entfernt; keine Kinder ergeben eine leere Sammlung, sofern die Mindestkardinalität dies erlaubt.

[cols="2,2,3"]
|===
| Control | Default | Bedeutung
| Parent input transform / Child input transform | leer | Die beiden direkten Eingangstransforms
| Parent key field | `+_ili_tid+` | Elternschlüssel
| Child parent key field | `+_ili_parent_tid+` | Passender Schlüssel der Kindzeile
| Child index field | `+_ili_index+` | LIST-Position
| Models / Model dirs / Class / Structure | wie Explode | Gewählte Sammlung der Elternklasse
| Source object field | `+_ili_source_object+` | Elternobjekt zum Aktualisieren
| Strict LIST ordering (contiguous indexes) | an | Aufsteigende, lückenlose Positionen ab 0 verlangen
| Fail on duplicate index | an | Doppelte LIST-Indizes ablehnen
| Fail on child without parent | an | Kind ohne passende Elternzeile ablehnen
|===

Unter `Options…` finden Sie neben den Puffereinstellungen:

[cols="2,2,3"]
|===
| Control | Default für neue Konfigurationen | Bedeutung
| Child attribute paths (comma separated, empty: all) | leer | Projizierte Kindattribute auswählen
| Collect mode | `PRESERVE` | Strukturkind kopieren und nur projizierte Werte überschreiben
| Parent basket field | `+_ili_bid+` | BID der Elternzeile
| Child parent basket field | `+_ili_parent_bid+` | BID der Kind-Elternzuordnung
|===

`PRESERVE` verlangt ein kompatibles `+_ili_child_object+`. Konkrete zulässige Untertypen, ungewählte Attribute und verschachtelte Sammlungen bleiben erhalten. Fehlende oder inkompatible Carrier sind Fehler. `REBUILD` erzeugt das Strukturkind allein aus den projizierten Feldern; weitere Inhalte und der ursprüngliche Untertyp werden dabei nicht zugesichert. Bei primitiven Sammlungen wird `+_ili_value+` verwendet; ein Kind-Carrier ist dafür nicht erforderlich.

Eltern und Kinder müssen nach demselben Elternschlüssel aufsteigend sortiert sein. Mit BID-Feldern ist dies `(BID, Elternschlüssel)`. Elternschlüssel müssen eindeutig sein. Bei striktem LIST-Modus müssen Kindpositionen innerhalb einer Gruppe zusätzlich aufsteigend und lückenlos sein. Nach dem Filtern können Lücken entstehen: nummerieren Sie die verbleibenden Kinder pro Elternschlüssel ab 0 neu. Bei deaktivierter strikter Reihenfolge sortiert Collect die aktuelle Gruppe nach Index im Spill-Speicher; die Sortierung der Elternschlüssel bleibt Voraussetzung.

Ungültige Indizes, Kardinalitätsverletzungen und mehrdeutige Zuordnungen werden abgelehnt. Das Verhalten für doppelte Indizes und Kinder ohne Eltern richtet sich nach den gleichnamigen Optionen. Die Standardwerte sind strikt.

==== Alte und neue Pipeline-Dateien

Neue Explode-Konfigurationen führen den Kind-Carrier mit; neue Collect-Konfigurationen verwenden `PRESERVE` sowie BID plus Elternschlüssel. Beim Laden alter `.hpl`-Dateien ohne die neuen Optionen gilt das bisherige Verhalten: Explode ohne Kind-Carrier, Collect mit `REBUILD` und bisheriger Schlüsselwahl ohne BID. Das Laden migriert diese Semantik nicht automatisch. Wählen Sie für eine Umstellung die Optionen ausdrücklich und kontrollieren Sie beide Eingangsschemas.

=== INTERLIS Role Join

Role Join ergänzt Zielattribute einer einfachen Assoziationsrolle. Der Dialog enthält `Main input`, `Lookup input`, `Models`, `Model dirs`, `Class`, `Role`, `Main ref field`, `Lookup TID field`, `Output prefix`, `Fields to add` und `Max lookup rows`.

Die Lookup-TID ist standardmässig `+_ili_tid+`. Ein leeres Präfix wird aus dem Rollennamen abgeleitet, etwa `+Gemeinde_+`. `Fields to add` ist eine kommagetrennte Auswahl. `Fail on missing mandatory reference` und `Fail on duplicate lookup TID` sind standardmässig aktiv.

Der Join liest beide Eingänge abwechselnd. Noch nicht verarbeitbare Hauptzeilen werden gepuffert; die erste Ergebniszeile folgt erst nach vollständigem Lookup. Dadurch kann ein gemeinsamer Produzent beide Zweige versorgen. Nutzdaten und Index werden bei Bedarf auf Disk ausgelagert.

`Max lookup rows` begrenzt die Zahl gelesener Lookup-Zeilen auf standardmässig 500'000. Überschreiten ist ein Fehler; `0` erlaubt unbegrenzt viele. Dieser Grenzwert gilt unabhängig vom Speicherbudget. Der Lookup verwendet TIDs: in zusammengeführten Identitätsräumen müssen diese eindeutig sein. Für allgemeine skalare Referenzattribute mit TID/BID prüfen Sie eine entsprechend zusammengesetzte Join-Zuordnung in Ihrer Pipeline.

[[validierung]]
=== INTERLIS Validate

Validate ist ein eigener Dateiinput mit Diagnosezeilen. Es validiert die ganze bestehende Datei einschliesslich zweitem Durchlauf, unter anderem für Referenzen und dateiweite Regeln. Die Ausgabe ist kein Strom der validierten Fachobjekte.

[cols="2,2,3"]
|===
| Control | Default | Wirkung
| Data file | leer | Bestehende XTF-Datei
| Models / Model dirs | `%DATA` / Standard-Modellverzeichnisse | Modellquelle wie Input
| Validator config | leer | Optionale lokale **INI**-Konfiguration des Validators
| Max errors | 10'000 | Fehlergrenze; `0` unbegrenzt
| Validate attribute/role multiplicity | an | Kardinalitäten prüfen
| Stop after first error | aus | Vorzeitig stoppen
| Emit warnings | an | Warnungen als Zeilen ausgeben
| Emit info findings | aus | Informationen zusätzlich ausgeben
| Fail the pipeline when errors were found | aus | Nach vollständiger Diagnoseausgabe Pipelinefehler setzen
|===

Früher Abbruch oder Fehlerlimit bedeuten unvollständige Validierung und werden mit einer Abschlussdiagnose kenntlich gemacht. Ein erfolgreicher Pipeline-Lauf ohne `Fail the pipeline...` bedeutet daher nicht automatisch, dass die geprüfte Datei gültig ist. Explizite Einstellungen in der INI können Prüfungen beeinflussen.

Die 13 Diagnosefelder lauten in Reihenfolge:

[source,text]
----
_ili_severity, _ili_message, _ili_source_file, _ili_line,
_ili_column, _ili_model, _ili_topic, _ili_bid, _ili_class,
_ili_tid, _ili_attribute_path, _ili_constraint_name, _ili_raw_event_type
----

Zeile und Spalte sind Hop-Integer, die anderen Felder Strings. Nicht vom Validator gelieferter Kontext bleibt null. Bei einem Klassenconstraint kann dessen Name in der Meldung stehen, während `+_ili_attribute_path+` leer ist; `+_ili_constraint_name+` muss nicht diesen fachlichen Namen enthalten.

Aufgeschobene Validate-Fehler werden vor der Veröffentlichung vorbereiteter Writer-Dateien berücksichtigt. Alle Diagnosezeilen können noch bei nachgelagerten Transforms ankommen. Für eine gerade entstehende Ausgabe verwenden Sie stattdessen die Writer-Option `Validate before publication`.

=== INTERLIS Enumerations

Der Datei-unabhängige Modellinput benötigt `Models` und `Model dirs`. Er liefert `+enum_definition+`, `+enum_value+`, `+enum_path+`, `+parent_value+` (String), `depth` (Integer) und `+is_leaf+` (Boolean). So können Sie Enumerationswerte und ihre Hierarchie als Lookup-Tabelle verwenden. `+enum_path+` ist der qualifizierte Wertpfad; Klassenattribute enthalten den Elementpfad ihrer Enumeration.

[[puffer]]
=== Puffer und grosse Daten

Input, Object to Row, Role Join und Structure Collect haben unter `Options…` dieselben Einstellungen.
Mehrklassen-Output und Update zeigen sie im Hauptdialog:

[cols="2,2,3"]
|===
| Control / gespeicherte Option | Default | Bedeutung
| Buffer memory (MiB) / `bufferMemoryMiB` | 64 | Pufferbudget pro Transform; Teilpuffer teilen dieses Budget
| Spill directory (empty: system temp) / `spillDirectory` | leer | Java-Tempverzeichnis; alternativ ein beschreibbares Verzeichnis
| Maximum spill (MiB, 0: unlimited) / `maxSpillMiB` | 0 | Gemeinsame Disk-Obergrenze aller Teilpuffer dieses Transforms; 0 ohne zusätzliche Obergrenze
|===

Nutzdaten wechseln automatisch in temporären H2-Speicher. Cursor und temporäre Dateien werden bei normalem Ende, Fehler und Stop geschlossen beziehungsweise entfernt. Das Überschreiten einer gesetzten Disk-Grenze ist ein Fehler.

Input/Object to Row können bis Basket-Ende warten; Role Join wartet auf den vollständigen Lookup. Collect koordiniert beide Eingänge und hält die aktuelle Kindgruppe bei Bedarf auf Disk. Es sortiert erforderlichenfalls innerhalb dieser Gruppe, nicht den gesamten unsortierten Eingangsstrom.

Das Budget betrifft Puffer. Ein einzelnes IOM-Objekt, seine Geometrien und sein bearbeitetes Ergebnis müssen weiterhin in den Heap passen. Viele kleine Baskets sind deshalb nicht mit einem einzelnen sehr grossen Objekt gleichzusetzen. Für Planung und Messung sind maximale Heap-Belegung, temporärer Diskbedarf und Zeit bis zur ersten Ausgabe relevant.

=== Mehrere Klassen gemeinsam schreiben

Der neue Mehrklassenmodus von INTERLIS Output nimmt die typisierten Klassenströme
direkt entgegen und übernimmt die Basket-Gruppierung. Für explizite
Ereignisverarbeitung besteht daneben weiterhin folgender Weg:

Ein typisierter Zweig pro Klasse kann mit Row to Object zurück in dasselbe Envelope-Schema wechseln. Vor einem Transfer Output im Objektmodus müssen zusammengeführte Zeilen nach BID gruppiert werden. Stimmen Identitäten oder Referenzräume nicht überein, müssen sie vorher fachlich abgestimmt werden.

Ein `EVENTS`-Strom benötigt eine gültige Transferfolge. Einfaches Anhängen zweier vollständiger Transfers oder das ungeordnete Zusammenführen ihrer Ereignisse ist dafür ungeeignet. Bewahren Sie Grenzereignisse und Metadaten, oder bauen Sie die gemeinsame Folge ausdrücklich auf.

Die neue Datei wird nach Pipeline-Ende von einer Folgepipeline geprüft. <<beispiel-i,Beispiel I>> zeigt den vollständigen Ereignisweg und einen getrennten Prüflauf.


[[interlis-update]]
=== INTERLIS Update: gezielte Änderungen

Verbinden Sie normale Änderungszeilen mit `INTERLIS Update`. Im Dialog stellen Sie
Original XTF, Target XTF, Models (Default `%DATA`) und Modellverzeichnisse ein.
Original und Ziel müssen verschiedene Dateien sein, auch bei Symlinks/Hardlinks.
Die Zielpublikation erfolgt erst nach erfolgreichem Pipelineabschluss; Validierung
ist standardmässig an, Überschreiben aus.

Pro Eingang wählen Sie Transform, Elternklasse und Feldzuordnungen. Für
Objektänderungen bleibt `Structure path` leer. TID und BID werden ausdrücklich
zugeordnet und müssen zusammen mit der Klasse genau ein Originalobjekt bezeichnen.
Nur aufgeführte Fachattribute werden ersetzt, einschliesslich Geometrien und
Blättern einwertiger Strukturen. Ein zugeordneter null-Wert setzt das Attribut
undefiniert; unzulässige Werte scheitern an Mapping oder Validierung. Fehlende
Änderungszeilen lassen die betreffenden Originalobjekte unverändert.

Alle anderen Klassen, Referenzen und unterstützten Transfer-/Basketinformationen
werden aus dem Original übernommen. Unberührte Geometrien bleiben in ihrer
IOM-Darstellung. Doppelte/unbekannte Schlüssel, DELETE-Objektpatches, unvollständige
Transfers oder eine während der Verarbeitung veränderte Originaldatei verhindern
die Veröffentlichung. Referenzen, Rollen, Identitäten und Assoziationen sind keine
Änderungsziele. Neue Objekte, Löschen, Umklassieren und Modellmigration gehören
nicht zu diesem Modus. Eine erneut serialisierte XTF ist nicht byteidentisch.

[[struktur-update]]
=== Struktur-Update ohne Elternzweig

[source,text]
----
INTERLIS Input (Quellobjekt mitführen)
  → Structure Explode (gewählte Sammlung, Herkunftsschlüssel an)
  → normale Hop-Bearbeitung
  → INTERLIS Update (Original, Ziel, Strukturpfad, Feldzuordnungen)
----

Neue Explode-Konfigurationen geben `+_ili_update_ref+` standardmässig aus. Alte
Konfigurationen müssen `Emit structure update reference` unter `Options…`
aktivieren; ihr bisheriges Schema bleibt sonst unverändert. Explode benötigt
TID, BID und das ursprüngliche Elternobjekt. `Fields…` begrenzt die Kindfelder.

Im Update wählen Sie dieselbe Elternklasse, den Sammlungspfad (etwa
`Kontrollen` oder `Details.Tags`) und das Herkunftsfeld. Zielattribute der
Feldtabelle sind relativ zum Kind, beispielsweise `Pruefstelle`.

Der Herkunftsschlüssel merkt sich das ursprüngliche Vorkommen und die Prüfsumme
des Elternobjekts. Sortieren oder Filtern der Änderungszeilen ändert die Zuordnung
nicht: gefilterte Kinder bleiben erhalten. Anzahl, Reihenfolge, BAG-Duplikate,
Untertypen und nicht ausgewählte Inhalte bleiben erhalten. Verschachtelte
Sammlungen werden mitgeführt, aber nicht direkt adressiert. Primitive LIST/BAG
können über `+_ili_value+` aktualisiert werden; null, Hinzufügen oder Entfernen
von Vorkommen sind nicht zulässig.

Der Schlüssel muss aus demselben unveränderten Original stammen. Fehlende,
ungültige, doppelte, veraltete oder zum falschen Pfad gehörende Schlüssel sind
Fehler. Objekt- und Strukturänderungen dürfen gemeinsam zu Update führen, sofern
ihre Zielpfade nicht überlappen. Es wird zuerst gegen das Original geprüft.

Für den bewussten Neuaufbau einer ganzen Sammlung verwenden Sie weiterhin
Collect. Dort ersetzt der Kindstrom die Sammlung vollständig; Filtern kann Kinder
entfernen. Beim Struktur-Update bedeutet Filtern dagegen: diese Kinder unverändert
lassen.
